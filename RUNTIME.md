# Runtime

What actually runs, on which ports, and what must never be exposed. For the feature tour see
[README.md](README.md); for the cloud→self-hosted migration steps see the migration runbook.

## Shape of the thing

A React single-page app compiled to static files, plus a Supabase stack. There is **no
application server of our own** — no Express, no API layer we wrote. The browser talks to
Postgres directly through PostgREST, and the database's row-level security *is* the
authorisation layer. Get RLS wrong and there is nothing behind it.

One exception: a single Deno edge function (`visitor-access`) runs server-side, because it
needs the service-role key to mint sessions for visitors who have no password.

```
browser ──HTTPS──> reverse proxy ─┬─> static files (dist/)
                                  └─> Supabase gateway ──> auth / rest / storage / realtime / functions
                                                                              └──> Postgres
```

## Services and ports

Everything runs in Docker. Two supervisors, deliberately: the Supabase CLI owns its own
containers (it also owns migrations, and keeps the service versions consistent with each
other), while [`docker-compose.yml`](docker-compose.yml) owns the web server we put in
front. Ports are the defaults set in [`supabase/config.toml`](supabase/config.toml).

`scripts/start.sh` brings both halves up in the right order — Supabase first, since Caddy
proxies to it.

| Port | Service | Role | Public? |
|------|---------|------|---------|
| 8080 | Caddy container | Serves `dist/`, proxies API paths | **Yes** — the only port on the tunnel |
| 54321 | Kong gateway | Front door to all Supabase services | Via proxy only |
| 54322 | Postgres 17 | Every record | **Never** |
| 54323 | Studio | Admin console, *no authentication* | **Never** |
| 54324 | Inbucket | Catches outbound mail in dev | **Never** |
| 54320 | Shadow database | Used by migration tooling | **Never** |

Behind Kong on 54321, addressed by path:

| Path | Service | What it does |
|------|---------|--------------|
| `/auth/v1/*` | GoTrue | Sign-in, sessions, Google OAuth, magic-link generation |
| `/rest/v1/*` | PostgREST | Table reads/writes, RPC calls — all RLS-enforced |
| `/storage/v1/*` | Storage API | The `repair-photos` bucket |
| `/realtime/v1/*` | Realtime | Live message delivery for `repair_messages` |
| `/functions/v1/*` | Edge runtime | The `visitor-access` Deno function |

## The single-origin requirement

The browser calls the database directly, so **the app and the API must be served from the same
origin**. If `dist/` is at one address and Kong at another, sign-in breaks: cookies and OAuth
redirects are origin-scoped.

Caddy resolves this by putting both behind one port:

```
:8080 {
  @api path /auth/* /rest/* /storage/* /realtime/* /functions/* /graphql/*
  reverse_proxy @api {$SUPABASE_UPSTREAM:localhost:54321}

  root * /srv/dist          # dist/ is bind-mounted into the container
  try_files {path} /index.html
  file_server
}
```

`try_files … /index.html` is not optional — the app uses client-side routing, so a visitor
opening `/ticket` directly gets a 404 without it. This replaces the SPA redirect rule in
`netlify.toml`.

## Configuration

Two files, both gitignored, both required.

**`.env` — baked into the build, not read at runtime.**

| Variable | Value |
|---|---|
| `VITE_SUPABASE_URL` | The **public** origin, e.g. `https://frc-mac.tailXXXX.ts.net`. Never `localhost` — this string ends up in code running on visitors' phones. |
| `VITE_SUPABASE_ANON_KEY` | The stack's anon key. Public by design; RLS is what protects the data. |

> Vite substitutes these at build time. Editing `.env` changes nothing until `npm run build`
> runs again. This is the most common way to waste an hour here.

**`supabase/.env` — read by the stack at startup.**

| Variable | Value |
|---|---|
| `FRC_SITE_URL` | Same public origin. GoTrue builds OAuth and magic-link redirects from it. |
| `FRC_GOOGLE_CLIENT_ID` | Google Cloud Console OAuth client |
| `FRC_GOOGLE_SECRET` | Matching secret |

The service-role key is generated by `supabase start` and injected into the edge runtime
automatically. It must never appear in `.env`, in `src/`, or anywhere the browser can read.

## Trust model

The parts that are load-bearing for privacy, in rough order of how bad it is to get them wrong:

- **RLS on every table.** `is_volunteer()` requires `role = 'volunteer'` *and* `approved = true`.
  An unapproved volunteer account sees nothing. There is no admin bypass in the app.
- **Studio has no password.** Anyone who reaches port 54323 has full read/write on every
  visitor record. It is bound to localhost and must stay off any tunnel or port-forward.
- **`visitor-access` runs with `verify_jwt = false`** because visitors are signed out when they
  enter a ticket. It is therefore internet-reachable and unauthenticated by design, and does its
  own rate limiting: 8 failed sign-ins per 15 minutes and 5 registrations per hour, keyed on a
  SHA-256 of the caller's IP, recorded in `ticket_attempts`.
- **A ticket is a credential.** The full 8 characters (`482137-KM`) open that person's whole
  record. The 6-digit half alone is not sufficient and must never be treated as public.
- **Name + phone is also a credential.** `find_visitor_match` opens an existing record on 2 of 3
  matching details, a deliberate trade for visitors who lost their card. `profiles.last_claimed_at`
  is stamped on every such claim so the team can audit which records were opened this way.
- **Security-definer functions** (`is_volunteer`, `slot_availability`, `find_visitor_match`,
  `set_volunteer_approval`, `mark_thread_read`) run as their owner and bypass RLS internally.
  `find_visitor_match` is revoked from `anon` and `authenticated` — only the edge function may
  call it. Check those grants after any schema change.

## Requirements

Two installs, both via Homebrew:

- **Docker Desktop** — runs everything; give it ~4 GB of RAM
- **Supabase CLI** — applies migrations, supervises the stack

Node and Caddy are **not** required on the host. Caddy runs as a container, and
`scripts/build.sh` falls back to a `node:24-alpine` container when Node isn't installed.
If Node *is* present it is used instead, because a bind-mounted `npm install` is slow on
macOS.

Apple Silicon and Intel both work; all images are multi-arch.

### Container networking

The Supabase CLI publishes its gateway on the **host**, not inside the compose network, so
the Caddy container reaches it at `host.docker.internal:54321` (set as
`SUPABASE_UPSTREAM` in `docker-compose.yml`). The Caddyfile falls back to
`localhost:54321` when that variable is absent, so running Caddy natively also works.

## Running it

```bash
./scripts/bootstrap.sh   # first run: images, stack, schema, keys, build, web server
./scripts/start.sh       # every time after that
./scripts/stop.sh        # shut down, keeping data
```

What `bootstrap.sh` does, if you would rather drive it by hand:

```bash
supabase start            # boots the stack, prints the anon and service-role keys
supabase db reset         # applies supabase/migrations/ in order — rebuilds the schema
./scripts/build.sh        # compiles to dist/, baking in .env
docker compose up -d web  # Caddy serves dist/ and proxies the API on :8080
```

For frontend work, `npm run dev` on :5173 hits the stack directly and skips Caddy;
`http://localhost:5173` is already in the allowed redirect list.

`supabase db reset` **drops the database and rebuilds it**. It is the right command on a fresh
machine and the wrong one on a live server — once real bookings exist, use `supabase migration up`.

## Health checks

```bash
supabase status                                  # per-service state
curl -sI localhost:8080 | head -1                # Caddy serving the app
curl -s localhost:54321/rest/v1/ -o /dev/null -w '%{http_code}\n'   # gateway reachable
psql "postgresql://postgres:postgres@localhost:54322/postgres" -c 'select count(*) from repair_requests;'
```

## Known gaps

- **Nothing sends email or SMS.** Not a configuration problem — it was never built. Visitors are
  not told when a booking is confirmed, and neither side is notified of a message; the thread is
  only seen by someone opening the app. Do not assume the system chases anyone.
- **No scheduled backups.** `supabase start` gives a database, not a backup policy. On a
  self-hosted server that is now a person's job, not the platform's.
- **One-item-per-month is not enforced**, and walk-ins cannot be logged from the volunteer side.
